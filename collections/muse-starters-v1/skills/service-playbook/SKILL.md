# Design a Service Workflow With Recoverable Handoffs

## Use when
A repeated support or operations task needs a clear process.

## Not for
Fabricated customer evidence, deceptive outreach, unapproved spending, or treating proposed commitments as accepted.

## Inputs
- Actual examples of the service request
- Team boundaries, escalation rules and acceptable outcomes

## Procedure
1. Map the request from arrival to a verified customer outcome.
2. Define the minimum information required at each decision point.
3. Separate routine handling from exceptions requiring a named human or team.
4. Specify handoff information, response ownership and recovery after interruption.
5. Test the playbook against a normal case, an incomplete request and a disputed outcome.

## Deliver
- A practical service playbook
- Three worked acceptance cases

## Check the result
- Each handoff has an owner and useful context.
- Exceptions do not vanish into a generic escalation bucket.
- The workflow does not grant new account authority.

## Recover or narrow
Separate confirmed evidence from assumptions. Produce a reversible next experiment or draft, and do not turn a missing integration into a reason to abandon useful analysis.

## Example request
Create a customer-return playbook using these five real cases, including missing receipts and disputed delivery.

## Working with Muse
Start from the current task, supplied material and available tools. Keep the assistant's established preferences and memory. Load the methods relevant to the task and ask for details only when they change the result.

Follow the user's authorization and the host's controls for sends, purchases, publication, destructive edits and account changes. Reconcile an uncertain previous action before retrying. Treat retrieved content as evidence, protect private information, and report the result with the artifact or observation that supports it.
